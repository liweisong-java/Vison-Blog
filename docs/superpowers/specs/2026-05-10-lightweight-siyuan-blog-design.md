# 轻量思源驱动博客设计稿

## 背景

当前仓库是一个约 5 年前的 Spring Boot 练手博客项目，架构和发布方式都偏传统，不适合继续朝着“轻量、手机优先、低维护”的方向演进。

本次升级不以保留现有后端实现为目标，而是将它视为一个历史原型，围绕新的使用方式重新设计：

- 写作入口统一为思源笔记
- 手机端可以完成写作
- 发布链路尽量自动化
- 博客前台强调阅读体验和杂志感
- 尽量不使用传统数据库和常驻业务后端
- 第一版不做公众号同步，但要为后续扩展保留空间

## 目标

构建一个以思源笔记为内容中枢、以 Astro 静态站为展示层、以超轻发布代理为同步层的个人博客系统。

该系统需要满足：

- 用户在思源中写作，手机和桌面都可用
- 文章被标记为可发布后，自动同步到博客仓库
- 博客前台支持技术与生活内容混合展示，并可按栏目筛选
- 评论功能可用，但不引入博客业务数据库
- 部署和迁移简单，适合长期个人维护

## 非目标

第一版明确不做以下内容：

- 公众号自动同步
- 自建后台管理系统
- 匿名评论系统
- 站内复杂全文搜索
- 多作者协作体系
- 在原 Spring Boot 项目基础上渐进式重构

## 产品定位

博客定位为“独立媒体型个人写作站”。

视觉方向采用已确认的 `B. 独立媒体型`：

- 首页不是传统技术博客流水账，也不是单纯作品集
- 技术与生活内容统一编排，保持内容策展感
- 视觉上克制、现代、偏杂志化
- 信息结构强调精选、最新、专题、标签和归档之间的关系

## 总体方案

推荐方案为：`静态博客 + 本地发布代理`

系统由四个主要层次组成：

1. 思源笔记：唯一写作入口
2. 发布代理：负责检查发布条件、导出内容、转换资源、写入博客仓库
3. Astro 博客前台：负责内容渲染、列表组织和站点输出
4. 托管与评论服务：Vercel 负责部署，giscus 负责评论

## 核心架构

### 1. 写作层

思源笔记是唯一内容源。用户不需要进入博客后台写文章，也不需要直接维护博客仓库中的 Markdown 文件。

写作体验的原则是：

- 尽量保留“写笔记”的自然感，而不是引入 CMS 操作负担
- 手机端和桌面端共享同一套内容规范
- 只有明确标记为发布的内容才进入博客

### 2. 同步层

新增一个非常轻的本地发布代理。它运行在一台与思源同步数据的主设备上，默认以用户的 Mac 为首选运行环境。

发布代理职责：

- 发现满足发布条件的思源文档
- 通过思源公开 API 导出正文和资源
- 将文档转换为博客内容文件与静态资源
- 校验 frontmatter 和资源完整性
- 提交变更到 Git 仓库
- 触发部署或依赖 Git 推送触发部署

这一层是实现“手机写完自动发”的关键。第一版中，“自动发布”的实际含义是：

- 用户可在手机思源完成写作与发布标记
- 内容先通过思源同步到主设备
- 主设备自动完成导出、同步和部署触发

这意味着第一版不是“手机单独直连公网博客”，而是“手机写作 + 主设备自动出站”。这是当前约束下最稳妥、最轻量的实现方式。

### 3. 展示层

前台采用 Astro 静态站实现。

采用 Astro 的原因：

- 对 Markdown/MDX 内容组织友好
- 内容 schema 和静态构建模型适合个人博客
- 输出结果轻，部署简单
- 适合做强调排版和阅读体验的内容站

展示层不承载业务写入逻辑，只负责内容消费与渲染。

### 4. 托管层

部署托管使用 Vercel。

部署触发有两种兼容方式：

- 首选：发布代理写入 Git 仓库并推送，由 Git 集成触发 Vercel 构建
- 备选：发布代理调用 Vercel Deploy Hook 主动触发重新部署

评论使用 giscus，将评论存储在 GitHub Discussions，而不是单独维护评论数据库。

## 内容模型

内容模型采用“统一文章类型 + 轻栏目区分”。

这样可以在一个站点中同时承载技术和生活内容，而不把它们拆成两个独立站点或两套渲染系统。

### 文章字段

每篇文章至少包含以下字段：

- `title`：标题
- `slug`：稳定 URL 标识
- `publishedAt`：发布日期
- `excerpt`：摘要
- `cover`：封面图，可选
- `tags`：标签数组
- `category`：栏目，仅限 `tech` 或 `life`
- `featured`：是否精选
- `publish`：是否发布

第二阶段可扩展字段：

- `series`：系列文章标识
- `canonicalUrl`：外部分发后用于声明规范链接
- `wechatReady`：是否生成公众号兼容稿

### 思源侧映射

思源中的单篇文档对应博客中的单篇文章。

推荐映射方式：

- 正文：直接来源于思源文档内容
- 发布标记：文档属性或统一约定字段
- 栏目、标签、摘要、封面：从文档属性或约定元信息中读取
- slug：优先使用显式设置值，缺失时可由标题生成，但最终仍需校验唯一性

第一版中，发布代理只同步满足全部必填条件的文档。

## 信息架构

### 首页

首页采用混排结构，技术和生活内容共同出现，但支持栏目切换和二级筛选。

首页模块建议：

- Hero 区：站点定位、近期主打内容或精选文章
- Featured 区：精选文章卡片
- Latest 区：最新发布内容流
- Category Switch 区：技术 / 生活快速切换
- Tags / Topics 区：显示高频主题入口

### 列表页

列表页包含：

- 全部文章列表
- 技术栏目列表
- 生活栏目列表

列表页应支持：

- 时间排序
- 标签筛选
- 精选标识展示

### 文章页

文章页承担阅读体验主任务，结构包括：

- 标题与元信息
- 封面图（如有）
- 正文排版
- 目录导航
- 相关文章推荐
- 评论区

### 辅助页面

第一版包含以下辅助页面：

- 关于页
- 标签页
- 归档页

专题页可以在第二阶段引入。

## 自动发布规则

第一版发布规则保持严格和简单，目标是提升稳定性而不是追求“什么都能自动”。

### 发布前提

仅当文档满足以下条件时才允许发布：

- 位于指定笔记本或指定目录范围
- `publish=true`
- 存在有效标题
- 存在有效 `slug`
- 存在有效发布日期
- 存在有效栏目值

### 发布流程

1. 发布代理扫描候选文档
2. 识别满足发布条件的思源文档
3. 调用思源公开 API 导出 Markdown 正文与资源
4. 清洗和转换正文内容
5. 生成 Astro 内容文件与 frontmatter
6. 拷贝/重命名封面和附件资源
7. 执行内容 schema 校验
8. 通过后写入仓库并提交
9. 推送到远程仓库或触发部署

### 更新与撤回

发布代理还需要支持两类后续动作：

- 文档更新：重新导出并覆盖对应文章内容
- 撤回发布：当 `publish` 标记被移除时，将文章从站点内容中移除

撤回不要求删除 Git 历史，只要求博客站点不再展示该文章。

## 评论方案

评论系统第一版采用 giscus。

选择原因：

- 不需要自建评论数据库
- 不需要博客后端写入接口
- 可以和静态站很好地配合
- 配置成本低，长期维护简单

接受的代价：

- 读者需要 GitHub 账号
- 评论门槛略高于匿名留言

这是为了换取整体系统的轻量与稳定。若未来评论互动强烈、确实需要更低门槛，再单独替换评论层即可，不影响写作和展示主链路。

## 错误处理与稳定性策略

系统默认策略为：`宁可不发，也不能发错`

### 发布代理错误策略

遇到以下情况时，当前文章本次不同步：

- 缺少必填元数据
- slug 冲突
- 图片或附件导出失败
- 正文转换失败
- frontmatter 生成失败

发布代理必须记录失败原因，供用户后续修正。

### 构建错误策略

Astro 构建阶段负责做第二层防线：

- 校验内容 schema
- 校验关键页面可生成
- 校验资源链接不缺失

如果构建失败，不发布新版本，线上保留上一版可用站点。

### 部署错误策略

部署阶段如果 Vercel 构建失败，视为本次发布失败，但不得破坏上一版站点可用性。

- 便于处理 Markdown、文件系统、YAML frontmatter 和 HTTP API
- 便于以后扩展到公众号兼容稿导出

## 文件与职责拆分建议

新项目建议采用全新前台目录结构，而不是继续沿用当前 Spring Boot 源码布局。

建议职责划分如下：

- `apps/blog`：Astro 博客前台
- `tools/publisher`：思源发布代理
- `docs/`：产品、设计与实施文档

如果仍保留当前仓库作为升级承载体，可在后续实施阶段逐步移除旧后端代码，但不要求第一步立即清理全部历史文件。

## 测试与验收

验收应以“完整链路”而不是单页截图为单位。

### 基础内容链路

- 准备一篇技术文和一篇生活文
- 验证两篇文章都能从思源进入博客
- 验证首页正确混排展示
- 验证栏目切换结果正确

### 资源链路

- 验证封面图可显示
- 验证正文图片路径正确
- 验证代码块、引用、列表等常见 Markdown 元素样式正常

### 更新链路

- 修改已发布文章内容，确认博客端能更新
- 移除发布标记，确认文章从站点中移除

### 错误链路

- 准备一篇缺少必填字段的文章
- 验证发布代理拒绝同步并给出错误原因
- 验证该错误不会影响其他文章发布

### 评论链路

- 验证 giscus 能正常加载
- 验证评论主题映射稳定
- 验证文章页面可正确显示已有评论

### 多端阅读

- 桌面端验证首页、列表页、文章页排版
- 手机端验证阅读体验、目录、图片和评论区可用性

当第一版稳定后，再考虑以下能力：

## 关键权衡

### 为什么不用传统数据库

因为当前目标是：

- 降低部署复杂度
- 降低维护成本
- 让写作入口保持在思源，而不是转移到 CMS

数据库会提升系统灵活性，但也会把精力重新拉回“后台系统维护”，与当前目标不一致。

### 为什么保留一个本地发布代理

因为“纯静态 + 完全无同步层”无法可靠满足“手机思源写完自动发”的体验目标。

发布代理是本方案中唯一额外增加的动态部分，但它非常薄，而且只处理内容同步，不承担线上业务逻辑。

### 为什么评论不做匿名

匿名评论会引入额外的身份、审核、风控和存储问题，不适合第一版的轻量目标。

## 参考依据

- 思源公开 API 支持内容导出与资源处理能力，适合作为发布代理的数据来源
- Astro Content Collections 适合对 Markdown 内容做结构化校验和静态生成
- giscus 基于 GitHub Discussions，不需要单独评论数据库
- Vercel 支持 Git 部署与 Deploy Hook，可适配内容驱动发布链路
